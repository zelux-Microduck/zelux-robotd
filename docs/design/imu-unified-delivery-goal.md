# IMU 解耦：统一测试前的阶段目标

日期：2026-11-16。本文是本轮执行与交接入口，不取代 [IMU 机制与型号约束](imu-dxl-adaptation-plan.md)。

## 目标模式描述（可直接用于后续持续开发）

在现有独立仓库架构内，自动完成 IMU 多型号支持的可开发部分：保留 robotd 对共享 TTL 总线的唯一所有权，通过统一协议让 Studio 查询型号、驱动、固定安装方式和运行健康状态；通过明确确认的配置操作选择型号、持久保存并在用户确认安全后重启生效。配置值与实际运行值必须区分，离线、旧版本或读取失败不得显示为成功。每阶段完成后记录改动、自动验证结果和限制。最后停在“可交给用户统一测试”的阶段，提交统一测试方案，不自动部署、不接触真实串口、不使能舵机、不擅自提交或发布。

A1 使用飞特协议与固定竖装；B1 只确认固定横装，缺少协议证据，因此展示但禁止启用。不编造 B1 解码器。型号预设提供名义轴向映射；A1 的五姿态标定解算其到机体坐标系的三维修正，robotd 将修正与型号预设合成后用于控制输入，不把原始 IMU 坐标直接交给机体控制逻辑。

## 开发阶段与完成标准

1. 契约与 robotd 管理入口：可机读的型号目录、配置查看/原子更新和运行身份；复用参数校验，不兼容配置拒绝并保持原文件。
2. Agent 桥接：通过 robotd 工具/IPC 查询与配置，不打开串口；后台缓存状态，明确过期；显式安全确认才允许重启，不宣称保存即生效。
3. Studio 界面与标定隔离：型号、驱动、标称方向、当前运行的 IMU→机体完整映射、兼容性、待重启/实际生效、健康状态；提供五姿态采集、解算、保存与独立重启；总线来源不进入原 Agent I2C 标定。
4. 回归与交接：自动化测试、目标平台检查、协议示例、阶段总结与统一测试方案。无法执行的 Linux/板端项明确待测。

## 暂停边界

本轮可实现的软件闭环完成后交付测试文档并停止，等待用户统一测试。Linux Rust 测试、ARM64 链接产物、硬件时序和动作安全验收依环境记录。B1 实际协议适配、独立适配包正式发布、生产部署和签名发布缺证据时单列，不以占位宣称完成。
